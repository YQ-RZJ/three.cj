# 内存泄漏排查手册

> 本文是操作手册：任何人（开发者、测试、维护者）在怀疑引擎存在内存泄漏时，应按本文的 SOP 执行并提供可复现的台账数据。

---

## 1. 适用范围与环境

- 适用对象：引擎本体源码（`src/` 目录）及其调用方（`test/` 下的各类测试工程）。
- 平台约束：以 Windows x64 + MinGW/D3D11 为默认验证平台；仓颉编译器（`cjc`）与包管理器（`cjpm`）请使用仓库声明的最低版本及以上。
- 语言/运行约束：引擎基于仓颉语言与 bgfx 渲染后端；仓颉采用分代 GC，bgfx 采用显式句柄生命周期。**两类资源的泄漏判定标准不同**（见第 2、3 节）。

### 1.1 构建环境变量标准

按以下标准设定环境变量后执行 `cjpm build`：

| 变量 | 推荐值 | 说明 |
|---|---|---|
| `EXTEND_LIBS_PATH_WIN_X64` | 指向本地依赖库目录 | Windows x64 原生依赖搜索路径 |
| `EXTEND_LINK_OPTION_WIN_X64` | 空 | 额外的链接选项（一般留空） |
| `THREE_LOG_LEVEL` | `off`（内存测量）/ `info`、`debug`（功能调试） | **编译期**日志档位；`info/debug` 会引入日志分配的噪声 |
| `THREE_PROFILER` | `off`（内存测量）/ `all`、链路前缀（性能剖析） | **编译期**性能剖析开关 |
| `cjHeapSize` | 大型工程可设 `4GB` | 编译器 JVM/解析器堆大小，与运行时无关 |

> 注意：
> - `THREE_PROFILER` / `THREE_LOG_LEVEL` 是**编译期**开关，切换后必须重新构建才能生效；
> - 内存测量场景务必使用 `THREE_LOG_LEVEL=off` 与 `THREE_PROFILER=off`，否则日志/插桩自身的分配会污染统计；
> - 对比实验必须保持**完全一致的构建档位**，否则产物与分配行为不可比。

### 1.2 构建策略与资源约束

- 每个测试工程以静态链接方式编译整份引擎源码，**单次构建耗时长、资源占用高**，不要并发构建多个工程——并发会相互争抢 CPU/内存导致构建卡慢甚至失败。
- **构建必须逐项串行**：同一时间只构建一个工程；构建前确认没有残留的编译进程占用增量缓存。
- 需要验证的工程较多时，先做静态收敛（见第 5 节），只对可疑项做针对性重建，避免无差别全量构建。

## 2. 判定标准：什么才算“内存泄漏”

> 核心原则：**只看进程 RSS / 私有内存上涨，不能判定泄漏。**

### 2.1 判定为泄漏的充要条件

满足以下**任一**条件，才判定为内存泄漏：

1. **存活堆持续增长**：强制 `gc()` 后，`getAllocatedHeapSize()` 随帧数/迭代次数持续上升（多测点呈单调趋势，且增量远超噪声）。
2. **原生图形句柄持续增长**：bgfx 统计中的 `numPrograms / numShaders / numTextures / numVertexBuffers / numIndexBuffers / numFrameBuffers / numUniforms` 随帧数持续上升。
3. **原生内存持续增长**：外部采样（进程私有内存 `PrivateMemorySize64`）在跨越多个 GC 扩容台阶后仍保持上行（需与第 7 节的误判区分）。
4. **OS 资源持续增长**：进程句柄数、线程数、打开文件数等单调上升（文件/线程/事件等系统资源泄漏）。

### 2.2 反向判据（不算泄漏）

- 仓颉 GC 采用**延迟扩容 / 按代回收**，存活对象总量不变时，宿主进程的私有内存仍会阶段式（台阶式）增长后平台化——这是正常运行行为。
- 测点间出现单次台阶上升但之后平台化，且台阶量与 GC 扩容阈值吻合 → 大概率不是泄漏。
- 被测试代码本身**有意保留**的对象（如按用户操作新增的场景对象、缓存条目）会表现为合法增长，需结合业务逻辑判定，不应与“逐帧累积”混淆。

## 4. 资源所有权清单

排查的第一步，是建立各资源类型的**所有权账本**——创建点、销毁点、缓存键、缓存失效条件：

| 资源类别 | 创建点 | 销毁点 | 缓存键 | 缓存失效条件 |
|---|---|---|---|---|
| bgfx 资源 | `*_create_*` 系列 | 对应 `*_destroy_*` | 变体/几何/材质/纹理 id 等 | 对象删除、尺寸/变体变化、shader 重编译 |
| 原生内存 | `LibC.malloc` / 字符串转 C 指针 | 成对的 `LibC.free` / `AutoFreePtr` | — | 所有提前返回分支 |
| 线程/同步 | `SThread`、`spawn`、互斥/条件/信号量 | 退出与销毁 | — | 进程退出 / 资源注销 |
| 音频资源 | 解码器 / AL 缓冲 / PCM | 解码器释放 / 缓冲删除 / 内存释放 | 音频 id | 重复加载、销毁 |
| 物理资源 | Jolt 刚体 / 约束 / 形状 | destroy 配对（含级联） | body id | 刚体销毁、系统 shutdown |
| UI 资源 | ImGui 上下文 / 字体 / 字形 | 显式 finalize / 析构 | 字体配置等 | 上下文销毁 |
| 事件/缓存 | 事件监听注册、各类 map | 桶/条目删除 | 名称/类型键 | 引用移除后清空键 |

## 5. 静态审计方法

在写任何探针之前，先对代码做静态审计，标记可疑点：

### 5.1 五类必查项

1. **逐帧热路径是否调用 `*_create_*`**：任何在渲染/绘制/每帧更新中**无缓存**地创建资源的代码都高度可疑。
2. **重编译/重建路径是否先销毁旧句柄**：同一个程序（如 ShaderProgram）被第二次编译时，旧的 program / shader / uniform 是否释放。
3. **缓存是否有驱逐入口**：按对象 id 缓存的 map，在对象删除时是否有 `remove + destroy`；对本帧不再访问的缓存键是否有淘汰机制。
4. **异常/提前 `return` 分支**：创建资源后中途 `return` 是否泄漏（优先用 `AutoFreePtr` / `try-finally` 保证析构）。
5. **静态集合**：`static` 的 `HashMap` / `ArrayList` 是否只增不减（事件监听、窗口注册表、资源注册表、变换槽注册表等）。

### 5.2 条件判断方向审计

历史教训：**守卫写反**会直接导致逐帧泄漏。

- 例如 `if (Handle.isValid(...)) { 编译/创建 }` 会在“句柄有效”时每帧重复创建——属于把“仅在无效时创建”写成了“在有效时创建”。
- 审计时对 `isValid / isNone / size > 0 / isEmpty` 等守卫逐一确认**语义方向**与意图是否一致。

### 5.3 宏与条件编译约束

- 宏展开的代码中**不能出现条件编译指令**（编译器会报错）。
- 需要按编译器版本门控的字段，条件编译必须放在**普通顶层声明**上，不能放在被其他宏（如序列化适配器）修饰的类成员上。

### 5.4 常用检查清单

- [ ] 顶点/索引缓冲按对象与版本缓存，版本变化时销毁旧缓冲
- [ ] shader program 变体缓存 + 负缓存；重编译前释放旧句柄
- [ ] 阴影/后处理 Pass：跨帧复用的 program 只在首次编译，不使用帧本地重复编译
- [ ] 渲染对象缓存：本帧未访问键在帧末被驱逐
- [ ] 音频：重复 `load()` 前释放旧解码器/缓冲；`dispose()` 注销监听/变换槽
- [ ] 物理：销毁刚体级联销毁约束；shutdown 先释放约束再销毁系统；形状在成功/失败两分支都释放
- [ ] UI：每帧分配的原生字符串使用后释放；字体配置类有析构回收
- [ ] 事件：引用移除后键即刻清空，不残留空桶
- [ ] 窗口/输入：异常路径也执行统一清理；手柄 id 等临时数组两条路径都释放
- [ ] 网络/流媒体：重连、超时、关闭路径都释放旧 socket / 缓冲

## 6. 动态监控方法

静态审计只能**定位可疑点**，结论必须由动态监控给出。按“侵入度从低到高”分四级：

### 6.1 第一级：外部进程采样（无侵入，适合批量初筛）

对目标可执行程序做 60–90 秒周期采样，记录：

```
时间 / 工作集 / 私有内存 / 句柄数 / 线程数
```

判读要点：

- 必须观察**跨越多个 GC 扩容台阶之后**的尾段斜率；
- 尾段（最后约 20 秒）仍持续上行才可疑；
- 句柄数 / 线程数单调上升需单独记录（OS 资源泄漏）。

### 6.2 第二级：进程内 GC 存活堆（判定“存活对象是否真增长”）

在测试工程的每帧回调中加入**临时探针**（判定后删除），周期性强制 GC 并读取存活堆：

```cangjie
import std.runtime.*

if (frame % 300 == 0) {
    let before = getAllocatedHeapSize()
    gc()
    println("[heap] frame=${frame} before=${before} after=${getAllocatedHeapSize()} " +
            "gcCount=${getGCCount()} freed=${getGCFreedSize()}")
}
```

- `after` 值在多测点上平稳 → 无存活对象泄漏；
- `after` 值单调上升 → 真泄漏。

### 6.3 第三级：bgfx 资源计数（判定原生图形句柄泄漏）

周期性读取并打印图形资源计数：

```cangjie
let st = renderer.getStats()
let s = unsafe { st.value.read() }
println("[stats] programs=${s.numPrograms} shaders=${s.numShaders} " +
        "textures=${s.numTextures} vbs=${s.numVertexBuffers} ibs=${s.numIndexBuffers} " +
        "fbs=${s.numFrameBuffers} uniforms=${s.numUniforms}")
```

- 计数恒定 → 无句柄泄漏；
- 计数逐帧上升 → 存在 `*_create_*` 未配对释放。

> 建议每 60–120 帧打印一次；如需自动结束，可让测试在设定帧数后主动请求关闭窗口，保证测量窗口一致。

### 6.3.1 重建循环法（生命周期类泄漏的关键验证）

**适用范围**：仅“单次运行、句柄创建一次”的探针**测不出**生命周期类泄漏——例如 `EffectComposer` / Pass 在**重建、切换**时才创建新资源，若旧实例 `dispose()` 未释放其私有句柄，则每次重建都会累积。这类泄漏只有在重复创建/销毁同一资源链时才会暴露。

**判定方法**：在每帧回调中周期性执行“创建完整资源链 → 运行若干帧 → dispose 旧链 → 重建相同链”，同时打印资源计数：

```cangjie
import std.runtime.*

// 每 400 帧重建一次 EffectComposer 链，观察 uniforms/programs 是否随重建累积
if (frame % 400 == 0) {
    let st = renderer.getStats()
    let s = unsafe { st.value.read() }
    let before = getAllocatedHeapSize()
    gc()
    println("[rebuild] frame=${frame} uniforms=${s.numUniforms} programs=${s.numPrograms} " +
            "shaders=${s.numShaders} heapBefore=${before} heapAfter=${getAllocatedHeapSize()}")
    match (this.composer) {
        case Some(old) =>
            old.dispose()
            let nc = EffectComposer(renderer)
            nc.addPass(RenderPass(scene, camera))
            nc.addPass(BloomPass(...))
            nc.setSize(Int64(w), Int64(h))
            this.composer = Some(nc)
        case None => ()
    }
}
```

- 重建 N 次后，资源计数**恒定**（如 uniforms=27 恒不变）→ 生命周期释放正确；
- 计数随重建次数**线性增长**（每次 +K 个 uniform/program/shader）→ `dispose()` 未配对释放，逐一补 `_disposePassUniforms()` / `destroy*`。

> 实测：bloom_basic 上重建 6 次（2400 帧），uniforms/programs/shaders/textures/vbs/ibs/fbs 全部恒定，确认 `Pass._disposePassUniforms()` 修复有效。
> **加长单次运行帧数对这类泄漏无效**（句柄只创建一次）；必须用重建循环暴露。

### 6.4 第四级：Profiler / 堆快照（定位泄漏路径与对象类型）

- **Profiler（Tracy）**：用于确认泄漏路径的调用频率与耗时异常（例如“每帧都在编译 shader”会表现为热点）。内存面板只能看到显式打点的自管内存，看不到 GC 堆与 bgfx 内部句柄，故**不作为泄漏判定的主要依据**。
- **堆快照 + cjprof**：在可疑时刻导出堆数据，用 `cjprof heap` 分析对象类型与引用链。

> 实测注意：堆快照 API 在不同平台/运行时版本上行为可能不一致（可能生成空文件或长时间阻塞）。**优先用 6.2 / 6.3 判定，快照仅用于定位对象类型**。

## 7. 差分与验证

1. **基线对照**：以最简单场景（单个基础对象、无后处理/阴影）作为基线；若基线 GC 后存活堆恒定，则差异一定来自具体模块。
2. **修复前后对比**：同一测试、同一构建档位、同一运行时长、同一测量窗口，对比台账。
3. **资源计数回归**：修复后要求关键计数在数百帧内**完全不变**。
4. **功能回归**：修复句柄释放后必须运行对应测试确认画面/功能正常，避免误销毁正在使用的资源。

## 8. 常见误判与陷阱

1. **GC 延迟扩容**：宿主进程私有内存以固定台阶跳升后平台化，不是泄漏。快速判别：相邻采样差集中在 **64MB 整数倍**且台阶之间有平台期 → 大概率是 GC 扩容；真实逐帧泄漏通常表现为**连续、非量化、无平台期**的线性上行。结论必须回到 6.2 存活堆判定。
2. **bgfx 句柄不是 OS 句柄**：`numPrograms / numShaders` 增长不会体现在进程句柄数上，必须用图形资源计数统计。
3. **全量重建成本高**：static 链接整份引擎，构建耗时长；应先静态收敛再针对性重建，避免无差别全量构建。
4. **堆快照的平台差异**：见 6.4。
5. **宏档位影响产物**：不同日志 / 剖析档位会产生不同的代码与分配行为，对比实验必须保持档位一致。
6. **日志本身会产生分配**：`info/debug` 档位下字符串拼接会污染堆统计，内存测量使用 `off`。
7. **合法增长 ≠ 泄漏**：测试自身按操作阶段性新增的对象、缓存条目，属于合法增长，应与“逐帧累积”区分。

## 9. 标准排查流程（SOP）

1. 设置构建环境变量（见 1.1），`cjpm build` 通过。
2. 先跑**基线工程**：外部采样（6.1）+ 进程内 GC 存活堆（6.2），确认基线稳定。
3. 选定目标模块的测试工程（每个测试工程通常覆盖不同模块，见模块映射）。
4. 先做静态审计（第 5 节），标记可疑创建点 / 守卫 / 缓存，收敛范围。
5. 加临时探针（6.2 + 6.3），运行数百帧以上（按确定帧数自动结束，保证窗口一致）。
6. 判定（第 2 节）：
   - 存活堆或资源计数持续增长 → 泄漏；
   - 仅外部私有内存台阶式上升 → 记为“GC 扩容”，不算泄漏。
7. 修复：配对释放、缓存驱逐、守卫方向、`dispose` 清理、异常路径兜底。
8. 复测：资源计数恒定 + 存活堆平稳 + 功能正常。
9. **删除临时探针**，把运行方式、测量窗口与结论回填到排查台账（见 9.1）。

### 9.1 台账模板

| 字段 | 内容 |
|---|---|
| 被测工程 / 覆盖模块 |  | 
| 构建档位（日志/剖析） | `THREE_LOG_LEVEL` = ?，`THREE_PROFILER` = ? |
| 可执行文件 / 运行方式 |  |
| 运行时长 / 帧数 |  |
| 存活堆趋势（gc 后） | 平稳 / 台阶后平稳 / 单调上升 |
| 图形资源计数 | 各计数是否恒定，若不恒定说明变化规律 |
| 句柄 / 线程数 |  |
| 静态审计发现 | 可疑点与处理 |
| 结论 | 无泄漏 / 已修复 / 待复测 |
| 备注 | GC 扩容 vs 泄漏的判别依据 |

> 台账是后续回归的基线：同一工程、同一档位、同一窗口，结论必须可复现。

## 10. 局限性

- **外部采样无法读取仓颉堆**：存在 GC 扩容误判，确定性结论必须依赖进程内探针（6.2）。
- **图形资源计数只覆盖 bgfx**：CPU 侧的集合缓存、事件监听、线程等需静态审计 + 存活堆趋势综合判定。
- **动态增删资源场景的驱逐**：当前缓存机制在运行时动态删除对象/材质/纹理时可能缺少驱逐回调；长期增删资源的应用需要补充删除通知链与帧末驱逐机制。
- **工程数量多、单次构建耗时**：全量逐工程验证成本高；当需要覆盖所有工程时，应按模块映射抽样代表性工程做进程内判定，其余按 6.1 批量初筛，逐项串行推进。
- **平台与工具版本差异**：堆快照、运行时统计等行为可能随编译器 / 运行时版本变化，结论应注明验证环境。
